# invest-cli 性能与缺陷治理报告

日期：2026-09-19  
范围：`~/.agents/skills/invest-cli`（scripts/ 全量 + 测试）  
方法：先诊断后修复；每项结论均以实机测量为依据，无法复现的推断不写入。

---

## 一、重新定义问题

用户的原始问题是「最大的性能瓶颈在哪里」。第一性拆解后，日常单次调用的
耗时并不由「网络本身有多慢」决定，而由三个可独立优化的因子决定：

```
单次调用耗时 = 探测开销(判据是否可信)
             + Σ 串行网络段(是否重复付 RTT)
             + 真实取数成本(网络本质)
```

实测结果推翻了三处直觉假设：

| 直觉 | 实测 |
| --- | --- |
| 「31s 是 Yahoo 慢」 | 是 yfinance **库内写死 30s** 超时，且该源根本不可达 |
| 「有缓存，应该很快」 | `_common.py` 缓存**全仓零调用者**，从未生效 |
| 「按优先级选源就行」 | 优先级排序**不验证可达性**，把死源排在活源前面 |

## 二、瓶颈定位（按量化影响排序）

### P0-1 · us 路径 31s 硬超时

- **现象**：`invest-cli us AAPL` 稳定耗时 31.3s（3 连测 31.33/31.03/31.24）。
- **根因**：`sources/route.py:57` 的 `detect()` 对 python 型数据源只做
  `importlib.util.find_spec`——**模块装了就算可用**。yfinance 因此被判可用、
  按 priority=40 排在 us 链首位（bitget=35 在后）。而本机 Yahoo 完全不可达
  （`curl` 实测 `http=000`），yfinance 库内把每个端点超时写死为 `timeout=30`
  （1.2.0 的 `data.py` 内 9 处字面量），于是每次调用先烧满 30s 再回退 bitget。
- **决定性验证**：同代码、同数据源，**仅改顺序**：
  - yfinance-first → **31.33s**
  - bitget-first → **0.669s**
  证明 31s 完全来自「可达性无关的排序」，而非网络本质。
- **修复**：
  1. `registry._probe_python` 由 `find_spec` 升级为**真实 HTTPS 探测**
     （2s 预算、只读状态码、异常归一化）。
  2. `cmd_us._bound_yfinance_timeouts()` 给 requests/curl_cffi 设连接预算。
  3. `fetch_us_data` 的 `info` 与 `history` 由串行改并发（互不依赖）。

> **踩坑记录（重要）**：首版用 **TCP 握手**做可达性探测是错的。本机 TCP
> connect 到 Yahoo 在 0.01s 就「成功」（本地 PAC/透明代理应答），而真实 HTTPS
> 10s 不返回（`curl` 实测 `connect=0.000000s`、`total=10.06s`）。TCP 可达性是
> **假信号**，会原样保留该 bug，并因叠加探测把耗时变成 61s。必须用真实 HTTPS。

### P0-2 · 探测假阳性（P0-1 的根因层）

可用性判据与真实能力脱节：`datasources` 输出「yfinance 可用」，
实际每次调用都失败。用户据此排障会被误导。已由 P0-1 的修复一并解决。

### P0-3 · `_common.py` 缓存/并发三件套为死代码

`get_cached` / `set_cached` / `parallel_execute` / `query_eastmoney_parallel` /
`eastmoney_query_with_cache` **全仓零调用者**；`~/.cache/invest-cli` 下 12 个
json 是 7/31 的历史残留，从未被读写。等于「宣称有缓存，实际每次全量重取」。

同时 `sources/sec_edgar.py` 另有一份**真正在用**的 `_cached_json`
（TTL + 原子替换 + 写失败不阻断）。两份实现同一件事、只有一份生效。

**按奥卡姆剃刀收敛为一份**：删除全部死代码，把已验证的模式提升为
`cache_root` / `cache_get` / `cache_set` 单一真源，`sec_edgar` 改为复用。

### P0-4 · 探测开销在每次冷启动重付（最大收益项）

CLI **每次调用都是新进程**，而探测结果只存在进程内的 `_PROBE_CACHE`，
因此冷启动永远重付：实测 `pick("stock", market="a")` **2.958s**，
其中 yfinance 可达性探测 **2.02s**、命中缓存后仅 0.0003s。

**修复**：网络型探测结果**跨进程落盘**（原子写）。
- 冷：2.958s → 热：**0.026s**（**113×**）

**并且刻意采用非对称 TTL**：成功缓存 300s，**失败只缓存 20s**。
理由：一次网络抖动不该让一个可用源被禁用 5 分钟——负缓存过长是探测类设计
最典型的自伤（假阴性）。

### P0-5 · 数据可信度：模糊匹配冒充用户查询的标的

- **现象**：`invest-cli stock 不存在的公司XYZ` **exit=0**，输出一张完整的
  「行情快照」表（值全为 `-`），JSON 里却是 **Block Inc-A(XYZ.N)** 的
  ROE/毛利率——东财对未知标的做了模糊匹配。
- **危害**：用户以为拿到了自己查的那家公司。**静默错误比报错危险得多**，
  尤其是给 agent 消费时会被当作事实写进分析报告。
- **修复**：`cmd_stock.fetch_stock_data` / `cmd_fund.fetch_fund_data` 增加
  实体一致性守卫——行情/基础表为空而其余表有值 ⇒ 判为未找到，
  抛错并**指明实际匹配到的标的**（「已丢弃以免误导」）。

### P1 · 其余修复

| 项 | 问题 | 修复 |
| --- | --- | --- |
| 串行网络段 | `cmd_stock` 3 处、`cmd_fund` 6 处东财查询串行（N 段 RTT 相加） | 改并发，字段口径与降级行为不变 |
| 串行网络段 | `hithink.stock` 的 indicators 请求在并发批**之后**单独发 | 先用 `limit=1` 预算年报年份，再并入同一批（6 请求 0.408s） |
| 测试环境泄漏 | `test_route` 只 pop 环境变量、未屏蔽凭据文件，在**已配置的机器上必挂** | 同时屏蔽 env/凭据文件/rc，前提真正成立 |
| 错误信息被吞 | 新增并发助手笼统吞异常，把「缺 key」报成「东财为空」 | 配置类错误如实上抛 |
| stderr 噪音 | urllib3 `NotOpenSSLWarning` 污染错误通道 | 在 `import requests` **之前**装过滤器 |
| 缓存单真源 | `sec_edgar` 自建平台判断 | 复用 `_common.cache_root` |

> **stderr 修复的关键细节**：`NotOpenSSLWarning` 的继承链是
> `NotOpenSSLWarning → SecurityWarning → HTTPWarning → Warning`，与
> `UserWarning` **无继承关系**。实测用 `category=UserWarning` 或 `message`
> 正则**都拦不住**，只有 `category=Warning, module=r"urllib3.*"` 生效。

## 四、普适性验证（多环境 / 多场景）

**多场景**（15 项全通过）：A股/港股/基金/美股/SEC/选股/资讯/宏观/
datasources/capabilities，含名称输入（茅台）、港股回退（00700→eastmoney）。

**环境自适应**（关键：修复不是硬编码，而是随环境自适应）：

| 环境 | us 链 | 行为 |
| --- | --- | --- |
| Yahoo 可达（模拟） | `[yfinance, bitget]` | 走 yfinance，**保留全量财务**（ROE/回撤/行业） |
| Yahoo 不可达（本机真实） | `[bitget]` | 跳过 yfinance，2.6s 内返回报价 |

这证明「降低资源占用」没有牺牲能力：可达时全量字段照旧，不可达时才降级。

**异常输入**：不存在的标的 → 明确报错 + exit 1（原为静默假成功）；
非法代码 → 各源分别报明原因。

## 五、回归守卫

新增 `scripts/test_perf_guards.py`，**20 条**用例，全部经**红绿验证**
（还原旧行为→用例转红→恢复→转绿），覆盖：

1. 可达性判据——不可达的源必须判不可用；**可达时必须判可用**（防止修成一律拒绝）
2. 探针必须有界、必须缓存、**跨进程必须复用**
3. **负结果 TTL 必须远短于正结果**（防瞬时抖动被放大成持续不可用）
4. 探针异常必须 fail-open，不得外泄
5. 缺配置必须报配置错误，不得吞成「数据为空」
6. 缓存原子写、损坏按未命中、**死代码不得重新引入**
7. 模糊匹配不得冒充用户标的（含**反向用例**：合法查询必须仍通过）
8. stderr 不得被库噪音污染

测试总况：**120 passed / 0 failed**（基线 97 passed / 1 failed）。

## 六、工程巧思与设计取舍

1. **非对称 TTL**：正结果 300s、负结果 20s。缓存设计里最容易犯的错是
   对正负结果一视同仁，而二者的**代价结构完全不同**——缓存一次成功的代价
   是多探测一次，缓存一次失败的代价是误禁一个可用源。
2. **用「数据是否自洽」代替「名字是否匹配」**：实体守卫没有去做名称模糊比对
   （易误判），而是用「行情表为空而财务表有值」这一**结构性矛盾**判定。
   它不依赖任何字符串匹配规则，因此对不同市场、不同命名习惯都成立。
3. **删代码也是修 bug**：三件套死代码的真正危害不是占地方，而是**制造
   「已有缓存」的假象**，让后来者（包括我）基于错误前提做优化决策。
4. **探测判据必须与真实能力同层**：TCP 可达 ≠ HTTPS 可取数。判据的抽象层级
   选错，会得到一个「看起来在工作」的守卫——比没有守卫更危险。

## 七、对抗性审查与自我纠错

本轮邀请独立审查者对全部改动做对抗性复核，**推翻了本报告初版的一处核心结论**，
另指出两处真实缺陷。逐条记录如下（这类「自己抓自己」的记录比结论本身更重要）：

### 纠正 1（CRITICAL）：`_bound_yfinance_timeouts` 首版**完全无效**

初版做了两层，**两层都没生效**，却全程静默——典型的「看起来在工作」的死代码：

1. 打补丁的对象错了。`requests.Session.request` 与 yfinance 实际用的
   `curl_cffi.requests.Session` **无继承关系**
   （`issubclass(...)` → **False**），补丁打在了一个不会被调用的类上。
2. 选项码错了。curl_cffi 设置的是 **`_MS` 变体**
   （`TIMEOUT_MS`=155 / `CONNECTTIMEOUT_MS`=156，毫秒），
   而初版拦的是秒档 `TIMEOUT`(13)/`CONNECTTIMEOUT`(78)——curl_cffi 从不设它们。

**实测证据**：对「接受连接但永不响应」的端点发 `timeout=30` 的请求——
初版补丁下 **30.0s** 返回；改为拦 155/156 后 **3.00s** 返回。

**修正**：只拦 `_MS` 与秒档两组、各按单位取小；删除对 `requests.Session`
的无效全局补丁。并补上**计时回归用例**
（`test_bound_yfinance_timeouts_actually_bounds`），
该用例在旧实现下 **30.0s 失败**、在新实现下通过（已验证红→绿）。

> 教训：涉及"能不能生效"的补丁，**必须有计时断言**。只断言「函数被调用过」
> 或「补丁装上去了」是自证式的，抓不到这类完全失效。

### 纠正 2（HIGH）：实体守卫会误杀合法查询

初版判据是 `if not quote: raise`，把「行情表为空」当成了「未找到」。两处误伤：

1. **传输失败被当成标的不存在**。并发批里若恰好是行情那一组失败，会把一只
   正常股票报成「未找到标的」，甚至编出「模糊匹配到别家」的说明。
2. **停牌等合法情形**。停牌/无成交时行情为空但财务正常，会被整单拒绝。

**修正**：引入哨兵把「取数失败」与「成功但为空」彻底分开；
放行条件收紧为三条同时满足（行情请求成功 + ≥2 张表 entityName 一致 +
该名称与查询代码确有对应）。

> **修正过程中我自己又踩了一次**：第一版放宽写成「只要有表有值且名称一致」，
> 实测「不存在的公司XYZ」正是**只有 financial 一张表**有值 →
> 又原样返回了 Block Inc-A 的数据。已由
> `test_stock_single_other_table_does_not_authorize` 钉死。

### 纠正 3（HIGH→已修）：负结果缓存 TTL

初版对成功/失败一视同仁缓存 300s，一次网络抖动会让一个可用源被静默禁用
5 分钟。已改为**非对称 TTL**（成功 300s / 失败 20s），且**读取时**按存的是
成功还是失败分别判 TTL（只改写入侧不够）。

### 纠正 4（MEDIUM→已修）：探测缓存键缺缓存根目录

缓存键为 `("http", url)`，不含缓存目录 → 切换 `INVEST_CLI_CACHE_DIR` 后
仍命中上一个目录的条目（实测可复现），测试隔离被绕过。已把缓存根并入键，
并补守卫用例。

### 纠正 5（MEDIUM→已修）：两处无效的告警抑制

`os.environ.setdefault("PYTHONWARNINGS", ...)` 对**运行中的进程无效**
（该变量只在解释器启动时被读取），是纯死代码；
且 `category=UserWarning` 拦不住该告警。已删除死代码、统一为
`category=Warning, module=r"urllib3.*"`。

### 审查确认正确的部分

`_common` 缓存收敛、`sec_edgar` 复用、请求原子写、`test_route` 隔离修复、
`hithink` indicators 并入并发批——均经独立复核认可。
`hithink` 有一处**语义细节**被指出：预览失败时 indicators 会被整体跳过
（旧实现会用 history 的年份再试一次），属低影响差异，已记录为已知取舍。

### 仍未修（明确记录）

- 探测预算 2s 对**「连得上但很慢」**的端点仍是假阴性（无头模式实测
  `httpbin.org/delay/5` 会被判不可达）。理想做法是区分
  「DNS/连接被拒」（确定性不可达）与「读超时」（不可判定→放行），
  当前只对**抛异常**做 fail-open。已记录，未在本轮引入分类逻辑以免扩大改动面。
- 默认缓存根是用户真实目录，未加 `conftest.py` 级别的全仓隔离；
  当前仅由 `test_perf_guards.py` 的 autouse fixture 覆盖。
