## 一、重新定义问题

用户的问题是「最大瓶颈在哪、还有哪些低级 bug、有没有一行消灭一类的巧思」。
上一轮把「探测开销」与「可达性判据」修掉后，本轮先用同一套方法重测，得到的
结论与直觉不同：

```
日常单次耗时 = 探测开销(已归零)
             + Σ 串行网络段(是否重复付 RTT)   ← 本轮主要收益
             + 真实取数成本(网络本质)
             + 上游库的固定代价(日志/超时/错误形态)  ← 本轮主要缺陷来源
```

三个反直觉的实测结论：

| 直觉 | 实测 |
| --- | --- |
| 「有缓存，热路径应该都快」 | `fund` 的**深取**从不缓存，主快照命中缓存后仍每次重付 1.0s |
| 「argo 已经接上了」 | 接上了，但本地白名单把 250+ 引擎砍到 20 个，其中 1 个已不存在 |
| 「yfinance 只是慢」 | 慢之外还**抛库内 TypeError**、把原始 HTTP 响应体打进 stderr、对类别股返回空壳快照 |

## 三、缺陷清单

### D1 · argo 引擎白名单漂移（正确性，用户可感知）

- **现象 A**：`invest-cli info <词> --engine cn-web-search` 返回 `ok: true`、
  `results: []`，note 写「cn-web-search 无结果（尝试换 engine 或改检索词）」。
  用户会以为「真的没有这条资讯」。
- **根因**：`sources/argo.py` 维护的 `FIN_ENGINES` 里有 `cn-web-search`，
  而 argo v2.8.9 的 250+ 引擎里**没有这个名字**（`grep` 全仓零命中）。
  argo 在 stderr 打 `未知引擎: cn-web-search` 并以 exit 0 退出，
  本模块只看 stdout，于是「引擎不存在」被降级成「没有结果」。
- **现象 B**：`--engine anysearch`（合法引擎）被 `if engine not in WHITELIST`
  **静默替换**成 eastmoney，用户要的通用检索变成了财经资讯，且无任何提示。
- **现象 C**：`--max-results` 未透传，`argo.search(limit=10)` 仍只回 5 条
  （argo 默认值），limit 参数形同虚设。
- **修法（删而非补）**：删除整个白名单与静默替换分支，引擎名原样透传；
  无结果时的原因改为**引用 argo 信封里的 errors**（不再本地猜「缺 key」）；
  引擎合法性改由 **argo 自己裁决**：先问一次 `--list-engines`（磁盘缓存 1h），
  不在清单里就在**发起检索之前**拦下，给出具体路径的清单命令。
  净删 15 行常量与分支，同时解锁全部 250+ 引擎。

> **修法自身的坑（重要）**：第一版判据是「读 argo 的 stderr 看有没有 `未知引擎`」。
> 单测通过、冷路径实测通过，但**第二次同 query 就失效**：argo 命中自己的缓存后
> 直接回缓存信封，不再解析引擎，stderr 变空（实测同一 query 连跑两次：
> 第一次 stderr 112 字节，第二次 0 字节且 `cached: true`）。也就是说，
> 只靠 stderr 会让这个 bug 在**第二次查询时原样复现**，而第一次测不出来。
> 现改为以 `--list-engines` 清单为主判据（缓存命中无关），stderr 仅作
> 清单探测失败时的兜底。代价是每小时多一次 ~0.09s 的子进程。

### D2 · `fund` 深取永不缓存（性能，热路径白付）

- **现象**：`fund 110011` 主快照已命中磁盘缓存（0.12s 级别），但命令仍是 0.985s。
- **根因**：`cmd_fund.fetch_fund_with_fallback` 的 `_deep_fetch` 每次调用都起
  **两个 ttskill 子进程**（CLI 冷启动 + BASE_INFOS + HOLDING_INFO），
  实测占该命令全部耗时的 1.27s / 1.29s。缓存只建在主快照那一侧。
- **修法**：深取结果按 `CACHE_TTL_FUNDAMENTAL`（1h）落盘，只缓存成功结果
  （失败不缓存，避免一次抖动被放大成持续缺字段）；快照本身来自 ttskill 时跳过合并。

### D3 · FRED 四条序列串行取数（性能）

- **现象**：`intent macro` 稳定 2.4–3.5s。
- **根因**：`sources/fred.py` 的 `liquidity()` 顺序请求 4 条 fredgraph.csv，
  实测 2.34s 中 2.34s 全在网络（占命令总耗时 96%）。
- **修法**：4 条序列并发（互不依赖），并按 `CACHE_TTL_MACRO`（30min）落盘。
  隔离实测：串行 1.958s → 并发 0.637s。

### D4 · yfinance 对未知代码的三种失态（低级 bug 集群）

同一个「查一个不存在的美股」触发三条不同的坏行为，均实测：

1. **静默假成功**：`Ticker.info` 对未知代码返回**非空但无内容**的 dict
   （实测 `{'trailingPegRatio': None}`），快照因此全 None 却 `ok: true`。
2. **库内 TypeError 外泄**：`Ticker.history` 在 `_get_ticker_tz` 里抛
   `TypeError: argument of type 'NoneType' is not a container or iterable`，
   用户看到的「原因」是一句 Python 内部报错。
3. **stderr 被库噪音占据**：yfinance 用标准 logging（propagate=True、无 handler），
   每次上游错误都把**整段原始 HTTP 响应体**经 root lastResort 打到 stderr：
   `HTTP Error 404: {"quoteSummary":{"result":null,...}}`，把真正的错误行淹没。

- **修法**：加实体守卫（任一标识字段存在才放行，**刻意不含 `symbol`/`currency`**，
  因为它们是请求侧原样回显的）；把 future 异常归一为 `(值, 异常)` 供守卫判断；
  一行 `logging.getLogger("yfinance").setLevel(CRITICAL)` 掐掉库的裸输出。

### D5 · 类别股 `BRK.B` 拿到空壳快照（能力缺口）

- **现象**：`invest-cli us BRK.B` 返回 `symbol: "BRK.B"`、其余字段全 None，`rc=0`。
- **根因**：Yahoo 只认连字符写法（`BRK-B`）。实测 `BRK-B` 正常返回名称/价格/市值，
  `BRK.B` 返回空壳。旧断言 `normalize_ticker("brk.b") == "BRK.B"` 把错误行为当成了正确行为。
- **修法**：`^([A-Z]+)\.([A-Z])$` 命中的类别股写法转连字符。只对「纯字母基名 +
  单字母后缀」生效，因此不误伤 `0700.HK` / `600519.SS` 这类交易所后缀。

### D6 · 选股输出的「还有 N 条」算错（低级 bug）

- **现象**：`screen 市盈率低于10的银行股` 有 17 条结果，终端却写「还有 2 条结果」，
  而实际只打印了 10 行（少了 7 条）。
- **根因**：东财 `partialResults` 只带**首页 10 行**，`allResults.dataList` 才有全部 17 行。
  旧代码按固定常量 15 算剩余（`security_count - 15`），隐含假设首页有 15 行。
- **修法**：按实际打印行数算（`security_count - len(shown)`）。一行，消灭一类。

### D7 · 缓存写入的临时文件跨进程不原子（一致性）

`cache_set` 与 `registry._cached` 都把临时文件写成 `<name>.tmp`。CLI 每次调用都是
独立进程，两个进程写同一个键时：后写者截断先写者的临时文件，先写者的 `replace`
把半截文件搬到正式位置，后写者 `replace` 时 ENOENT 而丢缓存。
**修法**：临时名带 pid。两处各一行。

### D8 · 自选股落在缓存目录（数据归属错位）

`cmd_watchlist` 硬编码 `~/.cache/invest-cli/watchlist.json`：既是第二份路径知识
（`_common.cache_root()` 已经管这件事），又把**用户数据**放进了会被系统清理的目录
（macOS 会清 `~/Library/Caches`）。
**修法**：新增 `_common.state_root()`（数据与缓存分开，可用 `INVEST_CLI_STATE_DIR`
覆盖），watchlist 迁过去，旧文件读一次自动迁移、不删除。

### D9 · 文档与实现漂移（3 处）

| 位置 | 旧文 | 实际 |
| --- | --- | --- |
| `--engine` help / SKILL / docs | `eastmoney/zhihu/cninfo/cn-web-search` | `cn-web-search` 不存在 |
| `docs/data-sources.md` | 「`intent macro` 默认走 nbs_stats」 | FRED 结构化通道优先，nbs_stats 只是兜底 |
| `SKILL.md` screen 段 | 「支持自然语言条件：…『近1年收益>30%的基金』」 | `screen` 走东财 stock-screen，只筛股票；基金条件会被当成股票主营关键词 |

## 七、设计取舍与巧思

1. **删白名单比修白名单对**。引擎清单这类「随上游演进的外部事实」，本地维护
   一定会漂移，且漂移的表现形式是**静默错答**而不是报错。正确做法不是补全名单，
   而是把裁决权还给上游，并**把上游的诊断信号翻译出来**（stderr 的 `未知引擎`、
   信封里的 `errors`）。修完净删代码，能力反而从 20 个引擎变成 250+ 个。
2. **守卫的字段选择本身就是判据**。D4 第一版守卫把 `symbol` 算作「有数据」，
   实测 `BRK.B` 会得到 `{'symbol': 'BRK.B'}` 加一片 None，守卫形同虚设。
   教训与上一轮的「TCP 可达性是假信号」同源：**判据必须落在真实能力那一层**，
   回显字段不是证据。
3. **缓存要区分正负结果，也要区分主路与支路**。上一轮确立了非对称 TTL；
   本轮发现更深的一层：主快照缓存了，**支路（深取）没缓存**，等于缓存白建。
   缓存设计要按「一次调用会付几次网络/子进程」逐段核对，而不是看有没有缓存目录。
4. **数据与缓存必须分家**。缓存是可以随时删的东西，用户数据不是。把自选股
   放缓存目录，等于把用户资产交给了系统清理策略。
5. **跨进程原子写的隐含前提是「一个写者」**。`tmp + replace` 在单进程里原子，
   在多进程共用同一 tmp 名时不原子。这是「看起来对」的典型：读代码挑不出错，
   只有想到「CLI 每次都是新进程」才会发现。
6. **本轮最值得记的一条：我自己的修法接连三次「看起来在工作」。**
   ① stderr 判据单测全绿、冷路径实测也过，但依赖了上游一个未声明的前提
   （「每次都会解析引擎」），只在缓存未命中时成立；
   ② 类别股按字符串形状改写，`BRK.B` 通过了，却打断了 `VOD.L`，而断言里只有 `BRK.B`；
   ③ `use_cache=False` 只绕过读、仍然写，把测试的 mock 注进了生产缓存。
   三条同源：**判据（和断言）落在「通常成立的行为」上，而不是被声明的事实上**。
   正确的位置是 argo 的引擎清单接口、上游给没给数据、以及「不碰就是完全不碰」。

## 八、对抗性审查与自我纠错

本轮改动交给独立审查者做对抗性复核（不看我的结论，自己跑活数据）。它找到 **1 个 P0、
2 个 P1**，全部成立，逐条记录如下。这类「自己抓自己」的记录比结论本身更重要。

### 纠正 1（P0）：测试把 mock 写进了生产宏观缓存

`test_fred.py` 把取数函数换成 mock 后调用 `liquidity(use_cache=False)`，而第一版的
`use_cache=False` **只绕过读、仍然写**，且该测试文件没有隔离缓存目录。结果：mock 的
`100.0` 被写进 `~/Library/Caches/invest-cli/macro`，之后的**真实** `intent macro`
会命中这份假数据（审查者实测复现并清理）。

**修正**：两层防护。① `use_cache=False` 改为完全不碰缓存（不读也不写）；
② `test_fred.py` 加 autouse fixture 隔离 `INVEST_CLI_CACHE_DIR`。
并补两条守卫：`use_cache=False` 不得落下任何条目、部分失败不得写缓存。

> 教训：测试的「隔离」不能只做一半。`use_cache=False` 这个参数名听起来像
> 「不碰缓存」，实现却只做了一半，于是它成了把假数据注入真实环境的通道。

### 纠正 2（P1）：类别股按形状改写，打断了伦交所/德交所标的

第一版用正则把「纯字母基名 + 单字母后缀」一律改写成连字符。`BRK.B` 因此通过，
但 `us VOD.L`（伦敦）从**有数据变成报错**，而测试全绿——断言里只写了 `BRK.B`。

**修正**：撤销形状改写，改为「空壳回退」：点号形式拿不到任何标识字段时才试一次
连字符形式。判据从「字符串长什么样」换到「上游给没给数据」。实测
`VOD.L` / `VOW3.F` / `BRK.B` / `BF.B` / `BRK-B` 全部正常。
并补两条守卫：类别股必须按事实回退；点号形式已有数据时**不得**回退（否则
每次查伦交所标的都白付一轮网络）。

> 教训：这是本轮第二次踩同一个坑。D4 的 `symbol` 回显、D1 的 stderr 判据、
> 这里的字符串形状，都是「依赖通常成立的行为」而不是「依赖被声明的事实」。
> 判据选错层，测试再绿也没用——**因为断言也在同一层**。

### 纠正 3（P1）：FRED 部分失败也被缓存 30 分钟

`liquidity()` 只判断「有没有拿到任何序列」，四条里挂一条也照样写缓存，于是
「缺一条」的半成品被固定 30 分钟（净流动性可能因此算不出）。

**修正**：只在 `not errors`（四条全成）时写缓存。守卫：部分失败不得落下条目。

### 审查者确认正确的部分

`_identity_present` 未误杀稀薄标的（实测 SPY/IWM/VOO/ARKK/0700.HK/9988.HK/ADRs/
A 股后缀全部通过）、argo 未知引擎判据无假阳性（合法引擎 stderr 实测 0 字节）、
`--list-engines` 实测 243 个引擎且不含 `cn-web-search`、选股剩余条数正确、
yfinance logger 压制有效、无 future 泄漏。

### 审查者指出并已修的测试卫生问题

- `test_perf_guards` 里 cmd_stock/cmd_fund 的「传输失败」用例用**无锁计数器**
  （`calls["n"] += 1`）冒充「哪一路失败」。三组/六组查询是并发的，计数器会误判。
  已改为**按查询内容**判定（`"最新行情" in q`），确定性且与调度无关。
- 新增用例里 `monkeypatch.setattr(cmd_fund, "load_registry", ...)` 是死代码
  （`cmd_fund` 在函数内 `from sources import load_registry`，模块属性用不到），已删。

### 3. 删掉仪式性的代码，而不是把它写得更漂亮

- `sources/argo.py`：原先要从 stderr 里逐行解析出引擎名再报错。但 argo **原样回显**

- `cmd_watchlist.py`：读时迁移的逻辑内联在 `_load` 里，提成 `_migrate_legacy()`，

### 4. 给「类别股回退」一个名字

`cmd_us.fetch_us_data` 里内联了一段「点号形式空壳时试连字符形式」的分支，夹在
「取数」与「错误分类」之间。提成 `_resolve_snapshot(symbol) -> (info, info_err, hist)`，
于是 `fetch_us_data` 只剩两件职责：取快照、把「传输失败」与「标的不存在」分开报。

刻意**没有**改成「候选写法生成器 + 循环」：那需要额外的错误簿记才能保住
「报错要报用户给的那个代码」这条语义，反而更绕。现在的写法是两次显式尝试。

### 5. 把 screen 逻辑从入口文件挪回它该在的层

`invest_cli.py` 里内联着 `parse_markdown_table`（15 行）+ `cmd_screen`（57 行）共
72 行**选股专属**的终端排版，而它的兄弟命令（`cmd_sec` / `cmd_info` / `cmd_watchlist` /
`cmd_intent` …）都各自成模块。入口文件的职责是 argparse + 分发，这里漏进了业务逻辑，
属架构漂移。已提取为 `cmd_screen.py`（与兄弟同构：模块 docstring + `run(...) -> int`），
入口回到 263 行、每个命令都是一行转发。

副作用是测试也变简单了：原先要造一个假的 `_Args` 类再调 `invest_cli.cmd_screen`，
现在直接调 `cmd_screen.run("x")`，假参数类随之消失。

### 6. 三处按同一标准补的收尾

- `sources/argo.py` 的 `known_engines(use_cache=True)`：**没有任何调用方传 `False`**，
  是投机性泛化（真正的逃生口在 `fred.liquidity(use_cache=...)`，那里有测试在用）。
  删掉参数。
- `sources/argo.py` 的 `_unknown_engine_error` 自己又调了一次 `locate()`（第二次扫
  skill 根），而两个调用点手里都已经有 `p`。改为把 `p` 传进去，顺带把「路径是占位符」
  的分支删掉——报错信息里的命令必须是可执行的。
- `cmd_us` 里「取数尝试」的返回值原先是位置元组 `(info, info_err, hist)`，
  调用方得记住中间那格是异常。改为具名元组 `_Attempt(info, error, hist)`：
  读代码时看到的是 `attempt.error`，不是「三元组的中间那个」。
  这是本报告第七节第 2 条教训的正向应用——把判据/契约写在类型上，而不是靠位置约定。

## 十一、口径与假设（哪些是判断，不是实测）

用户的要求里有几处需要在开工时做判断。逐条记录，便于事后核对：

| 判断点 | 我采取的口径 | 依据 / 风险 |
| --- | --- | --- |
| 「这个 invest 系列技能」指哪一层 | 以数据层 `invest-cli` 为主，分析层（SKILL.md/references）只做一致性核对 | 性能与 bug 的落点全在数据层；分析层是纯文档，无运行时。事后补了分析层的 WIP 入库与全家族一致性核查 |
| 「最大的性能瓶颈」 | 指**日常单次调用**的耗时，不是峰值吞吐或内存 | 与上一轮报告的口径一致（单次调用耗时分解）。未测并发/吞吐，本 CLI 也不是并发场景 |
| 「降低多余的资源占用」 | 指 CPU/网络/磁盘（缓存、子进程、重复请求） | 后来补测了 agent 侧的上下文成本：9 个技能的 description 常驻仅约 1122 tokens，SKILL.md 正文约 2.9 万 tokens，references 按需约 13.9 万 tokens。常驻部分不构成问题；references 偏大但按需加载 |
| 「一行修改消灭一类 bug」 | 指「一处改动消灭一整类缺陷」，不限于字面一行 | 实际交付里最接近的是缓存 tmp 名带 pid（1 行，消灭跨进程截断类）与 `setLevel(CRITICAL)`（1 行，消灭 stderr 噪音类） |
| 「让专业的技能来进行评估」 | 先用了独立 subagent 做对抗审查 | **这是本报告最该被质疑的一处**：用户明确说「技能」，而本机就有 `code-review` / `skill-auditor` 这类专项技能。事后补做了按 `code-review` 标准的自我复查（第十节）与技能体量/副本矩阵量化（第二节） |
| 「不同对话」 | 理解为不同的调用上下文（不同 cwd、被别的 skill 当库调用、冷启动） | 已按此实测。若用户本意是「多轮对话中的会话状态」，则本 CLI 无跨会话状态，唯一持久化是自选股，已迁到 state_root |
| 「未知使用需求的普适性」 | 用未配置机器、非法输入、类别股/交易所后缀、缺失 skill 树来代表 | 覆盖了「没配 key」「上游不通」「输入不存在」三类未知；未覆盖「从未见过的标的类型」（如期权、外汇） |
| 缓存 TTL 的取值 | 行情 60s / 基本面 1h / 宏观 30min | 依「上游数据的更新频率」而非拍脑袋：FRED 序列周度/日度，30 分钟内不可能变；ttskill 深取字段（同类分位/机构占比）变动远慢于行情 |
