## 一、重新定义「最大的性能瓶颈」

### 1.1 先量化「日常怎么用」，再谈优化哪里

前三轮把口径定为「日常单次调用耗时」。本轮补上此前缺的一半：**真实的调用形态**。
从 216 个真实会话文件（grok/pi/qoder/codex）提取 `invest-cli` 取数调用的时间戳，算同一会话内相邻两次取数的间隔：

| 间隔 | 占比 |
| --- | --- |
| < 60s（落在 60s 快照 TTL 内） | **80.0%** |
| 60-300s | 7.7% |
| 300-1800s | 12.3% |
| > 30min | 0% |

同一命令 + 同一标的的相邻重复调用（38 对）里，60-300s 只占 10.5%。

**这条数据推翻了一个我原本准备做的优化**：把 `us` 快照 TTL 从 60s 提到 300s。
按上表它只能惠及 4-5 次调用，谈不上「大幅」。**判定不改**（见第三节）。
同向证据：场景实测「先 `datasources` 再取数」比直取**慢 1.1s**（探测本身联网），
印证 SKILL.md「不要每次前置 datasources」是对的。

结论：**80% 的调用已经是缓存命中，所以「日常性能」= 缓存命中路径的耗时 + 每个标的的第一次取数**。

### 1.2 于是瓶颈全在「每次调用都走、但只有冷路径才需要」的东西上，都不在网络

对缓存命中路径做 `-X importtime`、逐模块自耗时统计，以及审查方的 `sys.addaudithook` 实测：

| 项 | 实测 | 为什么白付 |
| --- | --- | --- |
| `route.fetch` 先跑 `candidates()` 才判快照缓存 | `candidates()` = `yaml.safe_load` 2.7ms + import 链上每个适配器；`sources.bitget` 一带进来就是 `urllib.request → http.client → ssl` | 缓存键只由 `kind/market/arg` 决定，与候选链无关 |
| `cmd_stock` / `cmd_fund` 顶层 `import requests` | `import requests` 墙钟 +60ms（基线 0.01→0.07） | 只服务东财**兜底**；主路走 `route.fetch`（同花顺优先） |
| `sources/__init__.py` 顶层 `import yaml` | +10ms（0.01→0.02） | 只服务配置读取，缓存命中时不需要配置 |
| `cmd_fund._ttskill_deep` 把可用性判断放在深取缓存**之前** | 热跑仍有 19 次 yaml 导入事件（`stock`/`us` 是 0） | 可用性判断要 `load_registry()`；而深取字段本就「变动远慢于行情」，命中时与此刻是否就绪无关 |
| `us` 的 yfinance `trailingPegRatio` 补取 | 一次**串行尾部**请求，独立实测中位 131ms（范围 130-1144ms） | 该字段 invest-cli 从不读 |

### 1.3 修完的读数（基线 `1ae81fc` vs 现在，同机同缓存交替各 5 次）

| 命令 | 会话前 | 现在 | 提升 |
| --- | --- | --- | --- |
| `us AAPL`（缓存命中） | 0.05 | 0.03 | 1.7x |
| `stock 600519`（缓存命中） | 0.08-0.09 | 0.05 | 1.7-1.8x |
| `fund 110011`（缓存命中） | 0.09 | 0.03 | **3.0x** |

`us` 那段被砍掉的请求约 130ms，被上游 ±1s 的抖动完全淹没（见 2.1 的自我纠正）。

## 二、修复清单（19 项）

> 1-5 是性能，6-16 是数据层缺陷，17-19 是分析层与文档。守卫一律用「改动前的树」反向验证过会失败。

### 2.1 [perf] 跳过 yfinance 的 `trailingPegRatio` 补取 · `1f1748b`

**根因（逐 HTTP 请求打点）**：`Ticker.info` 在 `_fetch_info` 之后**必然**再调
`_fetch_complementary`，而它在 yfinance 1.x 里的**全部内容**就是为 `trailingPegRatio`
发一次 `ws/fundamentals-timeseries`。yfinance 源码自己的注释写着 "Very expensive for fetching just one value"。
实测它是 us 路径里**唯一不与任何请求并发**的一段（串在关键路径尾部）。而 invest-cli 从不读该字段。

**修法**：把 `Quote._fetch_complementary` 换成不发请求的等价实现（同样的幂等标记、同样把
`_info["trailingPegRatio"]` 置 None，键集不变）。逃生舱 `INVEST_CLI_YF_FULL_INFO=1`。

**验证（含一次自我纠正）**：
- 审查方用**确定性重放**（录制真实 Yahoo 响应体，两种模式喂同一份字节，消除网络波动）跑了 7 个标的：
  每标的恰好少一次请求（总请求 32→25），**逐字段差异 0**（含每一层键集）。
  这一点比我最初拿活体两次取数对比更严格，结论成立。
- 性能量我最初写「us 冷路径 3.82s→2.19s」——**这是两次单样本之差，不成立**。
  审查方 n=13 配对测不出差异；我自己随后补的 n=8 配对同样测不出（中位数两边都是 4.14s，
  配对差均值 +0.29s，方向还是反的）。真实节省 = 一次往返（中位 131ms）。机制成立、量级被抖动淹没。
- 审查方另发现：peg 端点传输失败时，FULL 会把整只票判成「yfinance 取数失败」，
  SKIP 不受影响、仍能如实报「未找到标的」——这是本改动的**额外收益**（不是回归），
  但也意味着「输出完全一致」只在成功路径上成立。
- 补丁鲁棒性：原实现只判「属性存在」，审查方注入 `def _fetch_complementary(self, extra)`
  证明签名变化时补丁仍会静默覆盖原实现。现已要求必填参数只有 `self`；逃生舱取值改为大小写无关
  （此前 `False` 与 `FALSE` 语义相反）。

### 2.2 [perf] 热路径去掉白付的重库开销 + 快照命中先于路由 · `00bddc9`

对应 1.2 表前三项。语义影响一处：「候选链为空 + 缓存新鲜」改为返回缓存
（旧代码报「无可用数据源」）。审查方确认这条**还有第二种触发方式**（未在提交信息里披露）：
`candidates()` 抛异常 + 缓存新鲜时，旧代码把异常抛给调用方，新代码返回缓存。
可达路径是 `load_registry()` 里的 `import yaml` 失败（PyYAML 缺失/环境损坏），
影响上限一个 TTL（fund 是 3600s）。判定为可接受（给新鲜数据优于报「无源」），但记入遗留。

审查方还用 `sys.addaudithook` 在 urllib3 **首次导入的那一瞬**检查 `warnings.filters`，
并用系统 python3（LibreSSL，能真实触发该告警）做对照实验，确认「过滤器先于 requests」的契约未破——
`-W always` 下三条真实入口 stderr 均为 0 字节。线程安全也实测过（8 线程同时首次导入无异常）。

### 2.3 [perf] `fund` 热路径一分没省（审查实测，修正我上一批的声明）· `dbd4e7a`

`cmd_fund._ttskill_deep` 把**可用性判断放在深取缓存之前**：判断要 `load_registry()` →
`import yaml` + 解析配置。于是 `fund` 热跑仍有 19 次 yaml 导入事件，而同结构的
`stock`/`us` 热跑是 0 次——我上一批声称的「热路径不再付 yaml」对 `fund` 不成立。
深取缓存里的字段本就「变动远慢于行情」，命中时与 ttskill 此刻是否就绪无关，因此先读缓存是安全的。

**实测**：yaml 事件 19 → 0；`fund 110011` 热路径 0.09s → 0.03s（**3.0x**，本轮单项最大收益，而 `fund` 按会话日志是使用频次最高的子命令）。

### 2.4 [perf] `stock` 走 yfinance 兜底时表格是空壳 · `42f48ad`

`--json` 有完整数据（`price 9.04 / pe_trailing 6.41 / market_cap 301084770304`），
终端却印「收盘价 - / 开盘价 - / 昨收 - / PE - / PB - / 总市值 -」，财务与年报两个区块整块消失。
根因：表格只认同花顺/东财的中文键。
**修法**：该形状直接交给 `cmd_us` 的渲染器（`title` 可覆盖为「行情快照（yfinance 兜底）」），
而不是在 `cmd_stock` 里再抄一份英文键映射。

### 2.5 [perf] 终端诚实度（顺带）· `41f0a72` / `ffeee37`

adapter 的 `note`（「行情缺失（可能停牌/无成交）」）此前被终端丢掉；跨源时同一 payload 的
`最新价` 不显示（终端只认同花顺键名）。现在别名命中时用别名当标签——实测 `stock 00700`
从「收盘价 -」变成「最新价 451.600」。Bitget 表格的浮点二进制尾巴（`339.33500000000004`）也修了。

### 2.6 [bug] 代码域不匹配返回冒牌数据（最严重）· `41f0a72` + `0ff11e1`

原状：`invest-cli stock 110011` 用东财的模糊匹配拿到「易方达优质精选混合(QDII)(110011.OF)」，
以**行情快照**名义输出，24 个字段 23 个 `-`，唯一数字是基金利润摆在「净利润」栏，rc=0、warnings 空。

**第一次修法不完整**（对抗审查发现并端到端复现）：守卫写在 `cmd_stock`/`cmd_fund` 里，于是

```
stock 110011              → rc=1 ✓
intent deep stock 110011  → rc=0，返回的正是要消灭的那张假快照
intent deep fund 600519   → rc=0，拿到盈米的 {"ok": true, "未识别到具体基金"}
```

**最终修法**：判据与守卫收敛到 `route.code_domain_error`，主路接在 `route.fetch` 的
「空标的」检查同层（都是「这个问题本身不成立」）；`deep fund` 那条先问盈米、不经 route，
在同一份判据上单独接。cmd_stock/cmd_fund 的重复实现删除，并加「不得有第二份实现」的 AST 断言。
只拦**确定段**（`000858` 这类与基金号段重叠的返回 None 仍放行）。

审查方用全表逐条测过误杀：任务列的与常见的 20+ 个输入（含 `fund 159915/512880/161725`、
`stock 000858/002594/茅台/AAPL/BRK.B/00700`）**没有一条被误杀**。

### 2.7 [bug] 输入层失败触发跨源猜测 → 同一输入返回两只不同基金 · `42f48ad`

实测 `invest-cli fund -1`：同花顺正确报「多个候选无法唯一消歧」，但 route 按「整单回退」
继续问 ttskill，而 ttskill 自己也会模糊解析——**同一输入在不同时刻返回两只不同基金**
（审查方实测先 003376、后 006961），rc=0、无告警。

**修法**：适配器用 `input_error` 标记声明这一类失败（产消两侧共用 `AMBIGUOUS_PREFIX` 常量），
route 见到标记即终止整链。`fund -1` 现在 rc=1 并列出候选。
**有意行为变更**：`fund 债券` 这类泛词以前返回一只任选基金，现在 rc=1 + 候选清单。
这与项目既有标准一致（`fund 张坤` 早已输出「东财模糊匹配到 张坤(基金经理)，已丢弃以免误导」）。

### 2.8 [bug] 可用性判据与凭据加载器漂移（同花顺/Wind 被静默移出链）· `8c9015b`

`sources/env.py` 的模块说明早就点名了这个漂移源，而 `hithink.detect()` / `wind._api_key()`
正是那样写的（只读 `os.environ`）。实测（key 只写在 `~/.zshenv`）：
`read_env` 与 `load_api_key` 都能读到，`detect()` 却报「缺少…且无凭据文件」。
registry 对 `env_or_file` 型**直接采信适配器判断**，于是同花顺被静默移出 A 股快照链、
股票落到东财（口径不同），`datasources` 还给出**错误原因**。修法：两处回退都改走 `read_env`。

### 2.9 [bug] 东财假可用信号 · `5309dbf`

东财是唯一没有适配器级 `detect()` 的 `env_or_file` 源，于是退到 registry 的通用回退——
它**只看文件是否存在**。实测（HOME 指向只含一行注释的 `eastmoney.env`）：
`registry.detect(eastmoney) -> (True, '读到 credentials.env')` 而 `load_api_key() -> ''`。
补齐 `detect()`（与其余源同一模式），报错还指出检查过哪个文件。

### 2.10 [bug] `screen` 把「上游没答」说成「未找到结果」· `8c97800`

### 2.13 [bug] `cmd_fund` 在 Python 3.9 上无法导入（预先存在）· `0ff11e1`

**实测**：`/usr/bin/python3 -m pytest scripts/ -q` → 237 passed（改前连收集都中断）。

### 2.14 [bug] `us .L` 股息率低估 100 倍 · `42f48ad`

### 2.19 [bug] 分析层：裸文件名引用（复核时才查出来）· `33bda18`

## 五、诚实的遗留

1. **`us` 冷取 3.5-4.9s**：`import yfinance` 0.50s（固定）+ getcrumb 0.6-1.2s +
   quoteSummary ∥ chart 0.8-1.6s + v7/quote 0.15s。已砍掉一段纯废请求（约 130ms），
   其余都在 yfinance 内部。**该路径的墙钟改善不可测量**，不要把它算作收益。
2. **探测预算 2.0s vs 稳态 0.58-1.05s**：出现过 1.94s 尖峰（97% 预算）。若某天网络更慢，
   会把健康的 Yahoo 判成不可达并负缓存 120s（静默降级到 Bitget 报价、丢掉财务字段）。
3. **`--json` schema 17 种**（本轮最大的结构债）：见第三节。
4. **对抗审查指出的一处未披露差异**：`candidates()` 抛异常 + 缓存新鲜时返回缓存而非抛错。
   可达路径窄（`load_registry` 内 `import yaml` 失败），影响上限一个 TTL，判定可接受。
5. **`fund 500001` 的提示是一段死路**：`stock 500001` 会说「是基金代码，请改用
   `invest-cli fund 500001`」，而 `fund 500001` 实测 rc=1（该封闭式基金已无可用数据）。
   分类正确、路由正确，但用户体验是个回弹。属提示文案粒度问题。
6. **`_common.eastmoney_api_key` 与 `sources/eastmoney.load_api_key`** 是同一件事的两份实现，
   行为不同（前者缺 launchctl/rc/凭据文件，异常 vs 返回空）。当前零调用者，
   但 `_common` 头注释把它当公共 API 面承诺出去了。
7. **probe 缓存目录不参与 `_prune_namespace`**：`registry._cached` 手写的 `.tmp` 落盘
   若 `replace` 失败会留下孤儿文件且永不清。量级极小。
8. **上游数据本身的问题（CLI 只做透传，无一致性护栏）**：`stock 五粮液` 的「FY2025」
   营收同比 −54.55% 与经营现金流只降 12%、ocf/净利 332% 互相矛盾（已直连上游确认是服务端给的）。
9. **`watchlist --with-quote` 的 `quote` 字段**装的其实是「名称 + 暂无价格的代码」；
   `add` 未校验代码格式（`zzzz` 可入库）。
10. **`screen --json` 透传 88KB**（东财原始信封 + markdown 表格串），agent 上下文成本高。
11. **版本 footer 不齐**：`invest-stock/fund` 标 v2.0、`invest-asset/allocation/macro` 标 v1.0、

### 我自己的两处失误（记录在案）

- **性能量高估**：把两次单样本之差（3.82s→2.19s）当成了收益。审查方用配对实验推翻，
  我随后独立复现了它的结论。教训：单样本对比在网络抖动 ±1s 的环境里没有分辨力。
- **守卫空断言**：新加的「技能名交叉引用」守卫首版用 `\b` 收尾，而 Python 的 `\w` 把汉字
  视作词字符，`invest-industry做` 之间**没有词边界** → 正则匹配不到 → 守卫在出问题的
  旧文本上也能「通过」。已改用负向断言，并加了「正则必须能抓紧贴汉字形态」的自检用例，
  再用「临时把悬空名塞回去」实测该守卫确实会失败。
- **检查器误报（复核时才暴露）**：「引用可达性」首版只认反引号包住的相对路径，还会把整条
  路径截成尾巴再去本目录找，于是把 3 个**正确写法**报成缺失（跨技能 `../invest-x/…`、
  skills 根相对 `invest-x/references/…`）。修好判据后才剩下 1 条真缺陷（裸文件名）。
  教训：检查器的假阳性会掩盖假阴性——它先让我以为「全家族引用都通」，
  而实际上它根本没能力检查那两类写法。
