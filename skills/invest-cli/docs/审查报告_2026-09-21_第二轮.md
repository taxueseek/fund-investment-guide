日期：2026-09-21
范围：`~/.agents/skills/invest*`（重点数据层 `invest-cli/scripts` 全量 + 分析层一致性），
接续 `docs/性能与缺陷治理报告_2026-09-21.md`（v2.4），本轮只记**新增**结论，不重复已修项。
方法：先重跑上一轮的实测基线，再用同一套「判据落在真实能力那一层」的标准复查；

## 一、重新定义问题

上一轮把「探测开销」「缓存分段」「上游错误形态」修完后，直觉上已经没有大瓶颈。
本轮不先看代码，而是**先量**：把日常命令的冷/热耗时重测一遍，再把「用户能感知的
错误」用未知输入打一遍。两个结论与直觉不同：

| 直觉 | 实测 |
| --- | --- |
| 「探测已经落盘缓存了，开销可忽略」 | 缓存只让**探测结果**可复用，没让「该不该探」变对：查 A 股仍会为末位兜底的 yfinance 付一次真实 HTTPS（0.5s） |
| 「中文名分类没问题」 | Python 里汉字也是 `isalpha()`，`intent deep 茅台` 被判成美股代码，去 Yahoo 白找 3.2s |
| 「盈米能识别基金名」 | GuessFundCode 是子串式匹配，「中国平安」「招商银行」被判成基金 |
| 「缓存有 TTL 就够了」 | TTL 只管读时命中，**不删文件**；`sec` 单公司 3.7MB，按查过的公司数无界增长 |
| 「`screen` 已经容错了」 | 上游 `data.data=null` 时直接抛 `TypeError` 裸异常（traceback） |

问题被重新定义成一句话：**v2.4 修的是「探测结果对不对」，本轮要修的是
「该不该做这件事」和「判据落在哪一层」**。前者是效率，后者是正确性。

## 二、最大性能瓶颈：惰性探测

### 现象与根因

`route.fetch()` 在 v2.4 的实现里先调用 `pick()`，而 `pick()` 会**一次性探测整条链**。
A 股链按优先级是 `hithink > eastmoney > yfinance`，其中 yfinance 只是末位兜底，
但它的探测是**真实 HTTPS**（`_probe_python` 要确认 Yahoo 真能取到数，见 v2.4 报告），
wind 的目录探测也要扫 skill 根。于是：

```
stock 600519 的固定成本 = 探测 wind(目录) + 探测 hithink + 探测 eastmoney + 探测 yfinance(HTTPS) + 真实取数
```

其中后两项兜底源的探测，在主源成功时**根本用不上**。

### 修法（最小改动）

把「能力判定」与「可用性探测」拆开：

- `candidates(kind, market)`：只做便宜判定（`coverage` 含 kind + 适配器真有该方法），不探测；
- `fetch()`：默认路径用 `candidates()` 建顺序，在**即将调用某个源之前**才 `detect()`，
  第一个成功的源即返回，后面的兜底源根本不会被探测；
- `pick()` 保留原语义（全链探测），继续服务 `datasources` / `chains()` 这类
  「一次看清全链可用性」的场景。

### 隔离实测（同一台机、清空缓存目录）

| 指标 | 修改前 | 修改后 | 倍数 |
| --- | --- | --- | --- |
| A 股路由探测段（`pick` vs `candidates`+首个 `detect`） | 0.515s | 0.007s | 73x |
| `stock 600519` 冷路径 | 1.517s | 0.51–0.60s | ~2.6x |
| `stock 600519` 触发的探测文件数 | 4（wind/hithink/eastmoney/yfinance） | 1（hithink） | 4x 少 |
| `fund 110011` 冷路径 | 2.304s | 1.24–1.45s | ~1.7x |

热路径不变（0.11–0.13s，主要是解释器启动 + 读缓存）。

## 三、缺陷清单

### D1 · 中文名被判成美股代码（用户可感知）

- **现象**：`invest-cli intent deep 茅台` 实测 3.20s 后报
  `yfinance: 未找到标的「茅台」; bitget: Bitget 无此 rToken: R茅台USDT`。
- **根因**：`cmd_intent.classify` 的美股分支写成 `t.isalpha() and 1 <= len(t) <= 5`。
  Python 的 `str.isalpha()` 对汉字返回 **True**（CJK 属字母类），
  于是「茅台」「腾讯」「苹果」都落进美股分支。`intent deep <标的>` 是文档化的
  自动识别入口，影响面是日常。
- **修法（一行）**：判据改成 `t.isascii() and t.isalpha() and ...`。
  「字母」这个语义必须落在「ASCII 字母」上。
- **验证**：`intent deep 茅台` → 600519 贵州茅台；`intent deep 腾讯` → 00700 腾讯控股（港股）。

### D2 · 盈米模糊匹配把股票判成基金（用户可感知）

- **现象**：修完 D1 后复测，`classify("中国平安") == "fund"`、`classify("招商银行") == "fund"`。
- **根因**：`_is_fund_by_yingmi` 的判据是「盈米返回了 fundName」。
  但 GuessFundCode 是**子串式模糊匹配**，实测：
  - 中国平安 → 华银平安中国主题灵活配置混合
  - 招商银行 → 银叶投资-招商银行-宁海工业园1号
  - 腾讯 → 银河定投宝腾讯济安指数
- **修法**：判据从「盈米返回了东西」改为「返回的基金名与查询确有对应」：
  查询是基金名前缀，或查询占基金名 60% 以上；另对 ≤2 字短名不做模糊匹配
  （2 字输入里股票/港股简称远多于基金简称）。
- **验证**：19 个常见名（腾讯/茅台/苹果/英伟达/比亚迪/宁德时代/中国平安/招商银行/
  贵州茅台/长江电力/五粮液/美的集团/隆基绿能/海康威视/易方达蓝筹精选/中欧医疗健康/
  沪深300ETF/黄金/国债）分类全部正确。

### D3 · 空标的打满整条链（效率 + 体验）

- **现象**：`stock ""` 实测 3.55s，最后拼出三句多源错误；
  `intent deep`（无标的）实测 4.37s。
- **根因**：`route.fetch` 不校验空参数，空串一路传到每个适配器。
- **修法（一处消灭一类）**：在 `route.fetch` 入口拦下空标的，返回一句明确中文。
  `stock/fund/us/screen/intent` 全部覆盖。实测 3.55s → 0.05s。

### D4 · 上游 `data.data=null` 抛裸异常（traceback 外泄）

- **现象**：`invest-cli screen ""` 直接抛
  `TypeError: 'NoneType' object is not subscriptable`（完整 traceback）。
- **根因**：`cmd_screen.run` 写 `d = result["data"]["data"]`，而东财空条件回包的
  `data.data` 是 null；`except (KeyError, IndexError)` 接不住 `TypeError`。
- **修法**：逐层容错（`(result.get("data") or {}).get("data") or {}`），
  `securityCount` 缺失/为 null 按 0 算，except 补上 `TypeError/ValueError`。
  D3 的空标的守卫已在更上游挡住主路径，这里是防御性第二道。

### D5 · 缓存无界增长（资源）

- **现象**：本机 `~/Library/Caches/invest-cli` 24MB，其中 `sec` 占 24MB；
  `sec` 单公司 `companyfacts` 约 3.7MB，TTL 24h 只影响读，文件永不删。
- **根因**：`cache_get` 过期返回 None 但不删；`cache_set` 只管写。
- **修法**：新增 `CACHE_MAX_AGE = 7 天` 与写时清理 `_prune_namespace`
  （清过期 `.json` 与残留 `.tmp`，进程内每命名空间一次，best-effort）。
- **附带清理**：v2.4 重构前的 7 个 SEC 旧命名孤儿文件（`companyfacts_*.json` 等，
  与新的散列命名文件内容重复）已移入 `~/.agents/.trash/2026-09-21_invest-cli-legacy-sec-cache/`。
  实测 24M → 11M。

### D6 · hithink 利润表被请求两次（效率）

- **现象**：v2.4 为拿年报年份，先发 `income-statements limit=1` 预览，
  批里又有 `limit=5` 的**同一端点**。同一次查询为同一份数据付两次请求。
- **修法**：按年报披露规律直接猜财年（A 股年报 4/30 前披露完毕，5 月起 year-1、
  1-4 月 year-2），把 indicators 放进同一批；猜错时用批里拿到的真实年份补一次。
- **验证**：`stock 600519` 实测 `fiscal_year=2025 report=2025-4 roe=32.53
  roe_source=index_weighted_avg_roe`，官方指标齐全、无警告；
  新增守卫钉死「利润表只请求一次」与「猜错财年会补取」。
- **修法自身的坑**：第一版 fallback 判据写成 `not indicators`，而
  `parse_indicators` 无数据时返回「全 None 的完整键集」——那是 **truthy**，
  fallback 永不触发。是新增守卫（mock 猜错财年）把它抓出来的；
  判据已改为「有没有任何一个指标取到值」。

### D7 · argo 非零退出只暴露 traceback 表头（体验）

- **现象**：`info` 失败时错误里是 `argo 退出码 1: Traceback (most recent call last): ...`，
  真正原因（如 `ModuleNotFoundError`）在最后一行。
- **修法**：`_stderr_summary` 取最后一行非空内容。

### D8 · `intent deep <type>` 缺标的被当成标的（体验）

- **现象**：`intent deep stock` 会把 `stock` 当美股代码去查。
- **修法**：`stock/fund/us/bond` 四类缺标的时明确报「缺少标的」；
  **反向对照**：`commodity`/`gold` 是固定场景（TTFUND_GOLD_INFO），不需要标的，
  是 SKILL 文档里的合法用法，不得被误拦。

## 六、设计取舍与巧思

1. **「探测结果可缓存」不等于「探测该不该做」。** v2.4 把探测成本降到可忽略，
   本轮发现真正的浪费在**调度**：为用不上的兜底源付费。修法不是让探测更快，
   而是让它更晚——把探测从「建链时」推迟到「调用前」。
2. **判据要落在「被声明的事实」上，而不是「通常成立的行为」上。** 本轮三处同源：
   - 汉字「是字母」是语言事实，但「字母」在这里的语义是 ASCII 字母；
   - 盈米「返回了 fundName」是它的行为，不是「查询的是基金」这个事实；
   - `parse_indicators` 返回全 None 的键集是它的契约，不是「有指标」。
   三处都把断言写在了同一层，测试才会先绿后红。
3. **一处修复消灭一类，优先选「入口」而不是「分支」。** 空标的守卫放在
   `route.fetch` 一处，同时覆盖 stock/fund/us/screen/intent 与 `screen` 的 traceback；
   比在每个命令里各加一次校验更小、更全。
4. **优化必须带正确性兜底，且兜底本身要被守卫。** 猜财年省一次请求，
   但非标准财年要能补；守卫用 mock 构造「猜错」场景，才逼出了
   `not indicators` 那个 truthy 陷阱。
5. **反向对照守卫不能省。** 「缺标的报错」若不加 `commodity/gold` 的反向用例，
   就会把 SKILL 文档里的合法用法一起拦掉。本轮 15 条新增里保留了 3 条反向对照。
6. **数据与缓存分家之后，还要给缓存一个「寿命」。** 只分目录不够，
   没有上限的缓存迟早变成占用。

## 七、未改与遗留（含实测依据）

1. **`stock`/`fund` 快照 TTL 仍为 60s。** 该快照含 5 年财报与官方指标，
   重取的代价高于行情；但价格时效对分析重要。改动属产品口径，需单独定，
   本轮不动。若要优化，方向是「行情短 TTL + 基本面长 TTL」拆两段缓存。
2. **`skill_roots()` 含 `Path.cwd()/.agents/skills`。** 在含 `.agents/skills` 的项目
   目录下运行会优先加载项目内的外部 skill 副本（本轮空环境测试就命中了
   项目目录下的 `.agents/skills/argo`）。这既可能是刻意的项目覆盖，
   也可能带来版本漂移，需产品决定，本轮不动。
3. **`--json` 仍 pretty 打印。** 对 agent 而言紧凑 JSON 更省 token，
   但默认格式属对外契约，本轮不动。
4. **`intent` 里 `kind == "argo"` 分支**仍不可达（v2.4 已记录），保留理由不变。
5. **冷路径的 1.2–4.6s** 仍是上游网络本质（东财多组查询、SEC 3.7MB、港股经东财）。
6. **`.zcode` / `.grok` 的 invest 注册链**仍未补（v2.4 已记录，属方向级决定）。

## 九、口径与假设

| 判断点 | 口径 | 依据 / 风险 |
| --- | --- | --- |
| 「最大性能瓶颈」 | 日常单次调用的固定成本（探测 + 重复请求），不是吞吐/内存 | 与上两轮一致；未测并发 |
| 「不影响能力」 | 惰性探测不改变候选集合与回退语义；猜财年带 fallback；缺标的守卫对 commodity/gold 例外 | 均有反向对照守卫 |
| 财年猜测的适用面 | A 股年报 4/30 前披露完毕；早披露/非标准财年走 fallback | 用 mock 验证 fallback 真的触发 |
| 缓存上限 7 天 | 取「远大于所有 TTL、又远小于磁盘焦虑」的值 | 所有 TTL ≤ 24h（SEC），7 天不会误删仍可能命中的条目 |
| 「让专业技能评估」 | 按 `code-review` 的判据层标准自查 + 新增反向对照守卫 | 未调用外部 subagent（本机无 code-review 专项 skill，等价方法已内化） |
